## Verified evidence and unresolved claims

The issue is open with zero discussion comments at inspection. Live master is 7ecacf124658cc1ec23cb6aae62622f2ace9bfd5. The inspected local installer, AGENTS and README blobs exactly match live master; installer blob is 2c9e862e7dd8a5887e89b8b74eab0ec6f4061b6b.

- Missing packages are reported, but their causal connection to the JFFS error is unproven. JFFS checking/transaction setup does not use jq. Readable format=0, scripts=1 and effective enable=1 already bypass the transaction.
- The generic JFFS message covers transaction-begin failures, including locking, snapshot/storage and NVRAM read failures. It does not uniquely identify incorrect JFFS settings.
- Preflight's JFFS helper currently checks only whether formatting equals 1. An isolated extraction of the real helper with a failed nvram-read stub returned format_pending=missing, result=OK, exit0. This proves a diagnostic gap, not the complete reported router failure.
- Automatic dependency helpers still exist at selected operation boundaries. Python/bcrypt are checked for password hashing and column for timezone setup; unconditional installation of all four packages at startup is not established as the correct fix.
- Argument-free startup assigns master and overwrites a saved installer source. Inspected explicit-ref update/re-exec paths preserve the supplied ref. A forced switch from an explicit tag to master remains a reproduction target rather than a proven path.
- Fresh unattended installation is deliberately rejected in both inspected current and v2.6.0-version source. Required first-run inputs are not supplied by --yes. Correct the contract and ordering; full unattended provisioning is a separate feature.
- Existing interrupted-transaction recovery can precede diagnostics/CLI rejection. Do not claim all such invocations make no changes; report recovery separately and preserve its safety contract.

## Revised intended behavior

### A. Independent, accurate readiness checks

Supported RT-AC68U-class older ARMv7/software-float systems with mounted Entware and valid JFFS settings must reach supported setup without a false JFFS failure because of missing action dependencies. Use stock-compatible checks before tools they do not require. Report each check's actual result and distinguish missing or unreadable values, known legacy absence, pending formatting, lock failures and snapshot/storage failures. Preflight must not report complete readiness when required reads fail.

Keep known legacy fallback/absent-key handling compatible. Never reset JFFS flags, schedule formatting or reboot merely to suppress an error. A pending format must still block setup. Report actual state/recovery outcome rather than a blanket no-changes claim when prior recovery occurred.

### B. Action-scoped dependency bootstrap

For the selected authorized install/update/setup operation, reuse functional providers and install or repair required missing/unusable providers before their dependent work. Probe the result after installation. Keep the existing alternatives and dependencies specific to the requested operation; missing optional packages must not block unrelated status/menu actions.

Clean-state preflight/status diagnose missing requirements without installing packages or starting new setup. An install path must not fail solely because a recoverable dependency is initially absent. A failed opkg/probe must name the dependency and failed stage. Preserve --force-depends --force-overwrite --force-reinstall on package-install/repair paths. Document mounted Entware/opkg prerequisites and automatic action dependencies separately from manual recovery instructions.

Existing interrupted-transaction recovery remains a separate, explicitly reported safety operation; this proposal does not silently bypass it to claim read-only startup.

### C. Predictable installer source/update policy

Resolve one installer source: explicit ref → saved INSTALLER_BRANCH → clearly reported default master. Preserve it through menu launches, checks, downloads and re-exec. Do not silently fall back to master when the chosen ref is unavailable or unsafe. Do not infer a tag pin from AI_VERSION or the filename of a downloaded script.

Keep installer source separate from AdGuardHome release/beta/edge selection. Show which component an update affects. Add a documented per-invocation opt-out for automatic installer-component updates, treating the installer and its matching service/helper scripts as a compatible bundle. An explicit ordinary update action must not silently override the opt-out. An AGH-binary-only update may proceed with the existing bundle only when compatibility is established; otherwise refuse before changes with a clear explanation. Do not leave an old installer orchestrating newly downloaded incompatible helper scripts. State flag precedence and persist the chosen policy through any re-exec before implementation. The opt-out must not disable artifact verification or implicitly change the AGH channel; replacement still requires applicable explicit authorization or selected policy. Test old-version reports against exact source/arguments before claiming every explicit-pin path is broken. New flags cannot retroactively change historical v2.6.0 binaries.

### D. Honest fresh-CLI contract

Retain --yes and topology-appropriate DNS/NVRAM consent protections. Do not treat these flags as complete timezone, credentials, WebUI, DNS/cache or other first-run configuration.

Until a separate explicit unattended-configuration contract is implemented, clearly document the non-interactive install path's existing-environment restriction and route fresh users to interactive setup or an applicable validated restore. Preserve the single-argument `sh installer install` interactive compatibility path for fresh setup; it is not the same invocation as flagged unattended installation. Reject unsupported requested work before ordinary configuration/source writes or downloads, while preserving separately required interrupted-transaction recovery. A passing preflight must not imply fresh unattended provisioning is supported. Test fresh `install --yes [--allow-dns-nvram]` refusal separately from successful interactive setup.

## DNS takeover requirement: firmware rebind and DNSSEC options

When AdGuardHome takes DNS ownership, remove the active directives implementing these firmware UI settings from every managed generated runtime configuration: main `/etc/dnsmasq.conf` and each supported/enabled SDN `/etc/dnsmasq-<index>.conf`.

| Firmware setting | Primary dnsmasq directive |
| --- | --- |
| Enable DNS Rebind protection | `stop-dns-rebind` |
| Enable DNSSEC support | `dnssec` |
| Validate unsigned DNSSEC replies | `dnssec-check-unsigned`, including valued forms |

The intended result is that these dnsmasq features are inactive while AdGuardHome owns DNS. Do not replace them with unsupported `=0` options. DNSSEC unsigned validation can be implicit when DNSSEC is enabled: current upstream firmware emits `dnssec-check-unsigned=no` when disabled, rather than a bare line when enabled. Removing `dnssec` is therefore essential even where no unsigned-check directive appears.

Inventory and explicitly handle the associated DNSSEC options emitted by each supported firmware, including `dnssec-no-timecheck` before NTP readiness and `proxy-dnssec` in the relevant privacy mode. Remove all active DNSSEC trust-anchor/key entries from each managed generated runtime configuration, including every `trust-anchor=` record, whether firmware-generated or custom, rather than only recognized root-key digests. Include DNSSEC-only key-file references where present; inspect included configuration so keys are not unintentionally retained through an indirect source. Preserve unrelated directives when an include contains mixed settings; do not delete an entire mixed-purpose include to remove keys. Persistent key files and custom source files remain available for native regeneration. Define the exact companion removal set before implementation and use exact directive names with valid whitespace/value/comment boundaries, without a broad prefix match. Unrelated rebind exception lists remain preserved.

Upstream mapping was independently checked in RMerl/asuswrt-merlin.ng, default branch `main`, `release/src/router/rc/services.c` lines 2289–2310, file blob `fc14bbebb54fa6c12070625ed9cb634dc69438bc`. Its rebind block emits `stop-dns-rebind` plus `rebind-domain-ok=dns.msftncsi.com`. Validate the actually supported 386/3006 firmware variants during implementation; this current upstream sample does not establish every older firmware's output.

Apply filtering within the existing staged `dnsmasq_params()` edit/publication path after its management/topology/handoff gates. Each main/SDN callback handles its own staged file and remains idempotent, including firmware regeneration and valid pre-start callbacks. Preserve existing overlap serialization, DHCP/local-DNS/IPSET behavior and per-file transaction failure propagation; do not introduce or claim an all-config atomic transaction.

Leave firmware NVRAM selections, persistent JFFS/custom source files and AdGuardHome's own security preferences unchanged. Unmanaged/native operation must not be filtered. On AdGuardHome stop, failed takeover or native DNS recovery, preserve existing rollback and firmware regeneration so main and enabled SDN dnsmasq regain the user's configured native behavior and listeners on port 53. Regenerate from current preferences rather than introducing a stale long-lived backup mechanism.

If mixed or nested includes require sanitized runtime copies, include those generated artifacts in publication/recovery: every reference must be valid before use, copies must survive required dnsmasq restarts, and unrelated included settings must remain effective. Unsafe or unreadable includes must stop takeover before a partially filtered config is published. Rollback/native recovery must restore valid references and remove generated copies only after they are no longer referenced. Do not mutate a shared persistent include used by another dnsmasq instance.

This removal guarantee applies to managed generated files and their effective DNSSEC key references at publication. Inspect preserved include references for DNSSEC keys and explicitly handle any DNSSEC-only reference or mixed configuration safely. Later user hooks can reintroduce settings; investigate/report that source without silently rewriting persistent user configuration.

## Pending recovery across reboot (#1045)

The same-boot backup-retention correction in #1041 does not cover a persistent
journal whose referenced `/etc` backup disappears at reboot. New journals must
retain their associated configuration durably with validated boot identity; a
new boot must not replay a stale generated runtime configuration. Legacy
journals without boot identity require an explicit validated reconstruction
boundary under the existing lock, preserving current main/SDN runtime or absence
and recovery provenance. Do not discard a journal merely because a backup is
missing. Cover main/SDN dispatch ordering, repeated and failed persistent
restoration, same-boot controls, signals, ownership and unsafe-path refusal in
the existing host/native recovery scenario. Physical reboot remains a separate
operator observation. TASK-038 tracks this correction and fresh CI qualification.

## Legacy uninstall compatibility (#1046)

An older installed manager may not implement `proc-restore`. Uninstall must
invoke that action only when a kernel-settings ownership journal requires it.
An existing journal still requires a working manager and successful restoration;
malformed or symlinked journal paths must stop uninstall without deleting state.
Cover absent-journal legacy dispatch, successful/failed restoration and unsafe
paths in the existing host/native uninstall fixture under TASK-038.

## Safe diagnostic export

Add a built-in opt-in support export using existing status, doctor and rollback information. Prefer an allowlist over raw tar archives of configuration directories. Include installer/AGH versions and source identity, router/firmware/architecture, Entware/storage/resource summaries, process/listener ownership, managed-hook checks and relevant failure/recovery stages.

Exclude passwords/authentication hashes, tokens, raw private configuration/NVRAM dumps, DNS query history and private client/domain/address details by default. Collection must be read-only and bounded in size/time, with safe paths and clean handling of missing Entware or failed writes. The operator controls whether anything is shared; no automatic upload or external database is required. Clearly separate diagnostic collection from separately reported recovery of an older pending transaction.

Acceptance: known secret-containing fixtures are sanitized/excluded, useful failure state remains interpretable, and export failures do not start a new install, change DNS/NVRAM/firewall or interrupt the service.

## Constrained-router resilience

Inventory existing tests before adding cases. Reproduce gaps for delayed/missing USB or Entware, full/read-only storage, failed download/extraction/write, interrupted operations and memory pressure. Preserve existing transactions, rollback, shared-hook content and preferences. Fix only demonstrated failures, in small focused changes; do not assume every test idea represents an existing bug.

Acceptance: failures return an actionable stage/result, retain the prior working state or clearly report recovery outcome, and preserve native DNS recovery. Separate real guest filesystem/process assertions from modeled firmware; USB reliability and physical memory pressure require hardware evidence. Any performance claim needs comparable measurements, especially on RT-AC68U; no speculative tuning or new default profile is bundled.

## Supported-channel lifecycle coverage

Existing beta/edge binary execution/config validation is not lifecycle proof. Test startup, ownership/listeners, TCP/UDP and local/reverse DNS as applicable, restart, shutdown, fallback/native DNS and conflict handling for each claimed architecture/channel combination.

Acceptance: candidate-bound reports identify the actual channel and behavior exercised; failures are fixed or the limitation is disclosed before release. Do not relabel execution-only tests as complete channel parity, skip failed cases to obtain acceptance or impose a fixed scenario quota.

## Acceptance and verification

1. Valid readable JFFS flags plus initially missing action packages: no false JFFS error, no unnecessary JFFS transaction; confirmed install uses existing bootstrap paths and reaches supported setup. Test exact entry point and capture narrowly scoped NVRAM values/exit statuses, installer identity/ref and failing transaction stage to reproduce the issue.
2. Failed NVRAM reads, known legacy-absent values, pending formatting, lock contention/path failures and snapshot/write failures have distinct honest results. Preserve transactional repair/rollback and do not expose full NVRAM inventory or secrets in diagnostics.
3. Missing/broken package providers are repaired only when needed and authorized, with canonical flags and functional recheck. Package failures report package errors. Clean-state diagnostic runs install nothing and perform no new setup changes.
4. Saved tag/no-argument, explicit positional/CLI refs, update opt-out, component-specific updates, re-exec, unavailable refs and checksum rejection retain source, channel, integrity and lock ownership contracts. No hidden fallback to master or checksum bypass.
5. Unsupported flagged fresh non-interactive invocation fails clearly without beginning the requested installation. Preserve successful single-argument interactive install compatibility, existing-environment update, validated restore and normal fresh interactive setup with established safeguards.

6. Main and multiple enabled SDN takeover callbacks remove the targeted active directives and required firmware companions, including duplicates, indentation, valued unsigned-check forms and the implicit unsigned-check case. All DNSSEC key/trust-anchor entries, including custom and multiple/root-rollover records, are absent from the managed runtime configuration; DNSSEC key-file references are handled without dropping unrelated included settings. Comments and unrelated options remain intact; repeated/overlapping callbacks do not reintroduce settings or corrupt files.
7. Inactive/unmanaged LAN and native recovery callbacks leave settings intact. AdGuardHome stop/failure restores or regenerates the user's native DNS behavior for all managed instances; persistent preferences and custom sources remain unchanged.
8. Staging, IPSET refresh, publication, interruption and compensation failures preserve the existing per-file configuration/recovery contract, including valid include references and lifetimes/cleanup of any generated sanitized copies. No partially filtered live edits or unrelated persistent source changes are introduced.

9. Diagnostic exports are useful, bounded and sanitized; malicious/secret-containing input and missing-storage cases do not leak private state or mutate service settings.
10. New resource/maintenance failure cases have actual failure evidence and focused corrections; successful paths, preferences, shared hooks and recoverability remain intact.
11. Each claimed stable/beta/edge lifecycle has actual channel/architecture evidence, separately identified from execution/config-only tests.
12. Final candidate software and physical evidence are traceable to their real tested inputs and scope; required current-head checks/reviews, checksums/versions and published candidate metadata agree.
13. Agent/test/command guidance remains aligned and optional external services do not become runtime dependencies, duplicate task ledgers or mandatory gates.

For the DNS takeover workstream, extend nearest `dnsmasq-lan-mode`, SDN lifecycle, startup handoff/native recovery and transaction-failure regressions; validate real dnsmasq configuration/service behavior as appropriate. Fresh selected-contract native evidence and relevant physical firmware checks are required after implementation; no new execution or fix is claimed by adding this requirement.

Start with nearest preflight/JFFS/jq/opkg, single-argument/source/version, re-exec/lock, checksum-policy and CLI tests. Add actual failing fixtures before code changes. Then run relevant host quality and fresh matching selected-contract evidence across armv5/armv7/armv8. The armv5 label remains older ARMv7 Cortex-A9/software-float, not a newer hard-float target. Firmware-specific NVRAM and Entware behavior requires candidate-specific physical confirmation on the affected RT-AC68U.
